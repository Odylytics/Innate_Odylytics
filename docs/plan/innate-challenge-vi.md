# Innate Challenge in Vietnamese (Telex/VNI)

> 25/11/2026. Extends [`innate-challenge.md`](innate-challenge.md). This is a **hypothesis + theoretical counting + feature-extraction code**. **There is no real Vietnamese typing data yet**: none of the benefits below has been measured.

## Scenario

After the PIN is entered, if Innate is unsure (low owner score, new recipient, large amount), it shows a Vietnamese sentence with tone marks, for example "Hôm nay trời đẹp quá" (The weather is so nice today), and asks the user to retype it. The sentence is generated by the server, so it is not private data. This step is combined with the PIN score and does not replace it yet.

## Why Vietnamese has an extra signal that English does not

Typing tone marks with Telex/VNI produces **transform keys**: keys that do not add a character but change the one already typed (`o` `w` → ơ, `f` → the huyền (grave) tone mark). There are 4 sources of personal difference:

1. **Telex or VNI** (letter keys or number keys).
2. **Position of the tone-mark key**: right after the vowel ("trowfi") or at the end of the syllable ("trowif"). This is exactly the idea "some people type this first, some type that first".
3. **How errors are corrected**: if the tone mark is wrong, backspace or type `z`, and the correction rate.
4. **Hesitation at the transform key**: pausing to think before pressing the tone mark.

Two other points worth noting for security:
- **Habits 1 and 2 do not depend on the specific sentence**, so they avoid the weakness found in E13 (a test sentence different from the enrollment sentence makes per-key-pair rhythm no longer comparable).
- **A bot must also imitate the input method.** A sentence with tone marks but no transform key at all (`vi_ime_coverage` = 0) means the text was set directly, pasted, `adb input text` (which bypasses the input method), or the keyboard has no Vietnamese. The server knows the minimum number of transform keys for the sentence, so it can check this without the content.

## Counting variants (E18, theoretical)

`research/experiments/e18_vi_variation.py`, result `research/results/e18_vi_variation.txt`. Only counts tone-mark positions × 2 input methods:

| Sentence | Transform keys | Number of ways to type it | Information ceiling |
|---|---|---|---|
| Hôm nay trời đẹp quá (The weather is so nice today) | 6 | 8 | 3.0 bits |
| Chuyển tiền cho mẹ ở quê (Transfer money to Mom back home) | 8 | 8 | 3.0 bits |
| Hôm nay trời đẹp quá mình đi uống cà phê nhé (The weather is so nice today, let's go for coffee) | 13 | 72 | 6.2 bits |
| Tuần này trời nắng đẹp quá (The weather is so sunny this week) | 10 | 96 | 6.6 bits |
| mua 4 ca phe 27 (no tone marks, control) (a buy-coffees phrase with digits) | 0 | 1 | 0 |

**Stated plainly:** the example sentence "Hôm nay trời đẹp quá" has only 8 ways to type it, so at most 3 bits, because only "trời" and "đẹp" allow a choice of tone-mark position. To get more variants, pick sentences with **many syllables that carry tone marks and have letters after the vowel** (nắng, tuần, uống, nhé). This is a **ceiling**: real people cluster into a few habits, so the real information is lower. Vietnamese adds one channel, not a channel strong enough to count as "much more secure".

## Phone-first design (25/11)

- **Lowercase sentences, letters and spaces only** (`scoring/challenge.py`): no Shift, no switching to the number layer, so typing rhythm is less noisy and both Telex and VNI can type it. Every sentence has ≥ 4 syllables with a tone-mark choice (checked by tests).
- **`GET /v1/challenge`** issues the sentence + an HMAC-signed token (`NHIP_CHALLENGE_SECRET`). The app sends the token back in `fields[name=challenge]`; the server knows the sentence without storing the typed content. A forged token is ignored. **Token reuse is not prevented yet** (no nonce store).
- **A phone does not see any keys** (Gboard reports `keyCode 229`, only composition events). So `sdk/innate-compose.js` infers transform keys from **the input length staying unchanged** (n = 0), and `cls` = null. Consequence: **Telex or VNI cannot be measured on a phone's web page** (`vi_vni_frac` is dropped, not guessed); it can only be measured on a computer keyboard or a native SDK. The rest (tone-mark position, error correction, hesitation, whether an input method is used) can still be measured.
- **Values assigned by script** (no `input` event) are detected by `finish()` as `set_text`. The same for malware's `ACTION_SET_TEXT` in a native app.
- **Turn off autocorrect/suggestions** (`autocorrect`, `autocomplete`, `spellcheck` = off); picking a keyboard suggestion is recorded as `paste` (length grows by > 1).
- **A native SDK (Android/iOS)** is the solid route: `TextWatcher.onTextChanged(count, before)` gives exactly this information along with `InputConnection`. Not written yet.

## What a person with a phone does (human measurement, 15 minutes)

Open `sdk/probe.html` (any host, or open the file) on: Gboard Telex, Gboard VNI, iOS keyboard Telex. On each, type "trời đẹp quá" (the weather is so nice) with the tone mark right after the vowel, then again with it at the end of the syllable. Send the log. The questions to answer: (1) is `keyCode` 229; (2) does the tone-mark key give `dLen = 0` (if the keyboard replaces the whole word, `dLen` is nonzero and the assumption is wrong); (3) does iOS have the `compositionupdate` event. If (2) is wrong, `vi_ime.py` must change how it recognizes a transform.

## Risks and unverified items

| Item | Why it matters |
|---|---|
| Does the SDK see transform keys? | Web on Gboard usually reports `keyCode 229` and composition events, not keys. Must be tried to know whether the SDK can compute `n=0` or only sees the text change. Needs a native SDK or a trial of `beforeinput`. |
| Input method rules | The count of tone-mark placements assumes the input method allows typing the tone mark after the vowel. Needs a trial on Unikey, Gboard, the iOS keyboard. Order of circumflex/tone marks, late w, and old/new tone placement style are not counted yet. |
| People without a Vietnamese input method | Cannot type a sentence with tone marks. Always keep an alternative path (a sentence without tone marks, or OTP). `vi_ime_coverage` = 0 must not lead to `hold` by itself. |
| People who change keyboards | Switching Telex↔VNI or changing devices makes the features jump. They must be learned over several sessions, not from one. |
| Data | Aalto is English, so it **cannot** check anything about Vietnamese. Need to collect Vietnamese people typing real sentences (team), with consent forms. |

## Suggested data collection (to measure for real)

20+ people, 2 sittings at least one day apart, 5 random sentences per sitting with ≥ 8 transform keys, on their own device (keeping their usual input method). Store `t, kind, n, cls`. Measure: (a) whether `vi_tone_late` and `vi_vni_frac` are stable between the 2 sittings, (b) FAR@FRR 5% when combined with rhythm, (c) how many bots typing via `adb`/set_text are caught by `vi_ime_coverage`.
