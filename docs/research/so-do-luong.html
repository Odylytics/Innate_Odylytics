Idea flow and how the models run

A PIN can be shoulder-surfed, but the way a person touches and types is hard to imitate. Innate reads the touch behavior when a transaction is confirmed, then recommends allow, step up, or hold. It never locks an account by itself.

Human/bot rules

Reliable on naive bots
Input
PIN, swipe and text-field features of one session.
How it runs
Each sign gives a suspicion score from 0 to 1: even rhythm (CV < 0.08), taps exactly on center, constant-speed swipes, set or pasted text. Takes the strongest sign.
Output
human = 1 − max, with reason codes.
Measured
Catches even bots and timing-noise bots 100%, only 5% of replay with noise, 1% of population-sampling bots (E4b).

LightGBM human/bot

Weak on unseen bots
Input
A fixed vector of ~30 features (NaN if missing).
How it runs
Gradient-boosted decision trees, learned from real StrokePIN people and team-generated bots. The score is mapped so the FRR 5% threshold equals 0.5.
Output
Score 0 to 1; the system takes the min with the rules.
Config
Off in the online demo build.
Measured
Bot type seen in training: replay 26%, population sampling 73%. Bot type left out of training: 9% and 20% (E4b).

Replay detection

Reliable up to ±10% noise
Input
The current session and the history of past sessions of the same account.
How it runs
Mean relative difference of key hold, key gap, plus center offset. Takes the nearest past session; ≤ 0.07 is replay.
Output
human forced to ≤ 0.1, so hold.
Measured
Catches 100% up to ±10%, 30% at ±15%, 1% at ±20%. Wrongly blocks the owner 0.28% (3 past sessions) to 0.64% (8 sessions) (E5b).

Owner check by distance

Weak, not a gate
Input
The session and the template (mu, sd of each feature).
How it runs
z = (x − mu) / sd, d = mean |z|, converted to a score with a sigmoid. The sd of timing features is shrunk toward the population variance (nu = 5) because there are only 3 samples.
Output
owner 0 to 1; 0 if there is no PIN evidence.
Measured
EER 0.20, FAR 0.57 at FRR 5% in the same posture; after a posture change EER 0.32 (E9).

LightGBM owner check

Better, still weak
Input
|z| of 24 features, without touch size (avoids learning the device).
How it runs
Learns which features matter more instead of treating all features equally. Runs only for a full 6-key PIN; a 4-digit PIN falls back to distance.
Output
Replaces the owner score, FRR 5% threshold is 0.5.
Config
Off in the online demo build.
Measured
FAR@FRR5% drops 0.573 → 0.375 (sitting), 0.944 → 0.708 (walking) (E12b).

Risk fusion

No optimal point
Input
human, owner, new recipient, amount off history.
How it runs
Weighted sum, then two thresholds A = 0.25 and B = 0.55. Not three sequential AND gates, because then the rate of wrongly blocking the owner compounds.
Output
risk, action, the contributions.
Measured
A = 0.25, 97 people (E29, with learned models): owner sitting allowed 76%, PIN-knowing impostor not allowed 78%. Raising A lets the owner through more easily but lets more PIN-knowing impostors in. Tuning the weights on data adds only ~2 points, so they stay as they are (E31).
