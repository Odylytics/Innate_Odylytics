# Innate — Hacker simulator

Member 2. Generates bot sessions with 4 tactics (section 5.1 of the plan), measures the catch rate per tactic, and attacks the demo phone for real via `adb`.

## Setup

```powershell
cd attacker
uv sync
```

API key: set `NHIP_API_KEY` = the **SDK** key; to use `--human-source api`, also set `NHIP_ML_KEY` = the **ML** key (to read `/v1/export`). The deployed key is in `backend/.env.deploy-key` on Member 2's machine. The default URL is `http://localhost:8000`; for the online version use `--api https://nhip-api-taupe.vercel.app`.

```powershell
$env:NHIP_API_KEY = "<key>"
```

## 4 tactics

| # | Tactic | How it is generated | Simulates |
|---|---|---|---|
| 1 | Evenly spaced taps, exactly on the key center | Key hold 60 ms, gap 140 ms, coordinates = key center, fixed touch size, straight swipe | Naive malware / `adb input tap` |
| 2 | Added timing noise | Hold 40–140 ms, gap 80–350 ms at random; still on the key center | Malware with basic evasion |
| 3 | Replay of a real session + noise | Take one real session, timing ±5%, coordinates ±2 px | Malware that recorded the victim's session |
| 4 | Sampling from the real human distribution | Each value (key hold, gap, center offset, touch size, swipe path) is drawn independently from all human sessions | Attacker with data from many people (Serwadda & Phoha 2013) |

Source of human sessions for tactics 3–4 (`--human-source`):
- `api` (default): sessions with `meta.role = genuine` pulled via `/v1/export` — **use once real data has been collected**.
- `synth`: synthetic human sessions generated by the tool — only for trying it out when there is no data yet.
- `file:<path.jsonl>`: one session per line in `SessionIn` format.

## Commands

### Generate "machine" data for Member 1

```powershell
uv run python -m nhip_attacker generate --api https://nhip-api-taupe.vercel.app --user acc_p01 --n 50
```

Sends sessions with `meta = {participant_id: "sim", role: "bot", tactic: 1..4}`. Member 1 pulls them via `GET /v1/export` (filter `meta.role == "bot"`). Sessions are only stored, not scored, so they do not affect the template.

### Measure the catch rate per tactic (slide figures)

```powershell
uv run python -m nhip_attacker report --api https://nhip-api-taupe.vercel.app --enroll-synth --n 40
```

- `--enroll-synth`: creates a target account `sim_target_*` that has completed 3 enrollment rounds. Tactic 3 replays another session of that account's owner.
- `--target <user_id>`: use a really enrolled account. **Careful**: a bot session scored `allow` with a high match score will update that account's template — do not run it on a real participant's account.
- `--new-recipient`: score as a transfer to a new recipient.

### Real attack via adb ("hacker control panel" demo)

Requires: Android platform-tools (`adb` in PATH), a phone with **USB debugging** on, and the demo wallet open on the PIN entry screen.

1. Get the key coordinates: on the phone enable Developer options → **Pointer location**, touch each PIN key, and note the X/Y shown in the top bar (device pixels).
2. Write them into `layout.json`:

   ```json
   {"1": [180, 1450], "2": [540, 1450], "3": [900, 1450],
    "4": [180, 1650], "5": [540, 1650], "6": [900, 1650],
    "7": [180, 1850], "8": [540, 1850], "9": [900, 1850], "0": [540, 2050]}
   ```

3. First print the commands as a dry run, then run for real:

```powershell
uv run python -m nhip_attacker adb --layout layout.json --pin 1593 --tactic 1 --dry-run
```

```powershell
uv run python -m nhip_attacker adb --layout layout.json --pin 1593 --tactic 2 --swipe 540 1800 540 900
```

Only tactics 1–2 are supported (adb taps exact coordinates). Each adb command takes ~50–300 ms, so the rhythm is not perfectly even — that is the "real malware" for the demo. Possible extension: an Android app using `AccessibilityService.dispatchGesture` (the actual malware mechanism).

## Measurement results (23/11, backend rule baseline, SYNTHETIC human data)

`report --enroll-synth --human-source synth`, 40 sessions/tactic, 3 seeds, local API; rerunning 20 sessions on the online version gave similar results:

| Tactic | Flagged (step_up + hold) | Notes |
|---|---|---|
| 1 | 100% (all `hold`) | Even rhythm + exact key center |
| 2 | 100% (all `hold`) | Exact key center still gives it away |
| 3 | 0% | Replay of the owner's own session: passes both the human/machine check and the owner check. **Update 24/11:** the backend now has a replay check (`scoring/replay.py`); on synthetic data it catches the ±5% noise of tactic 3 (see `research/results/e5_replay.md`) |
| 4 | 5–30% | Sampling from the human distribution: passes the human/machine check; the owner check is too lenient |

**Do not put on slides** — the humans are synthetic data. Re-measure once real data and Member 1's model are available.

Takeaways for the team:
- The baseline rules only block 1–2, as the plan predicted. Member 1's model 1 (trained on bot sessions produced by `generate`) is what has to raise 3–4.
- Tactic 4 shows that the owner match score mapping (`owner.py`, d = 2 → 0.5) is too lenient: samples drawn from other people are still treated as the owner. It needs calibration on real data (section 5.5).
- Tactic 3: replaying an old session almost identically is a strong signal — a real person never repeats the rhythm within ±5%. A "duplicate of an old session" check could be added in the backend.

## Input fields outside the PIN

`tactics.generate(..., with_fields=True)` adds `fields` (amount, recipient, note) per tactic, see `nhip_attacker/fields.py`: (1) set the text directly (`set_text`, no keys), (2) type evenly with no delete/paste, (3) replay the rhythm of a real human session (±5%), (4) sample the gaps and the delete/paste rate from the real-human pool. Off by default, so the old behavior is unchanged. Measurement results: `research/results/e11_text_field_bots.md`.
